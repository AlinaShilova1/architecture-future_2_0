# Обоснование архитектуры и конфигурации инфраструктуры "Будущее 2.0"

## 1. Философия подхода: Infrastructure as Code (IaC)

### 1.1 Почему декларативный подход с Terraform?
**Декларативный подход**, используемый Terraform, описывает **желаемое состояние** инфраструктуры, а не последовательность команд для её достижения. Для компании "Будущее 2.0" это критично по следующим причинам:

- **Идемпотентность**: Одно и то же определение инфраструктуры можно применять многократно с предсказуемым результатом
- **Воспроизводимость**: Разработка, тестирование и продакшен среды идентичны, что устраняет ошибки типа "на моей машине работает"
- **Версионирование**: Конфигурация хранится в Git, что позволяет отслеживать изменения, откатываться и проводить code review
- **Коллаборация**: Несколько команд могут совместно работать над инфраструктурой через стандартные процессы разработки ПО

### 1.2 Как IaC поддерживает бизнес-цели компании?
- **Ускорение выхода на рынок**: Новая функциональность (домен) может быть развернута за часы, а не недели
- **Снижение операционных рисков**: Дрейф конфигураций исключен, все изменения проходят code review
- **Масштабируемость**: Инфраструктура для нового партнера (фармацевтика) создается копированием и модификацией существующих модулей

## 2. Обоснование выбора ресурсов и их параметров

### 2.1 Сетевой слой (VPC)
```
CIDR: 10.0.0.0/16
Private Subnets: 10.0.1.0/24, 10.0.2.0/24, 10.0.3.0/24
Public Subnets: 10.0.101.0/24, 10.0.102.0/24, 10.0.103.0/24
```

**Обоснование:**
- **Изоляция доменов**: Разные подсети для медицинских и финансовых данных соответствуют требованиям регуляторов (GDPR, PCI DSS, HIPAA)
- **Multi-AZ архитектура**: 3 availability zones обеспечивают отказоустойчивость на уровне региона
- **Разделение публичных и приватных ресурсов**: Публичные подсети только для Load Balancer и NAT Gateway, все остальное в приватных

### 2.2 Настройки NAT Gateway
```
enable_nat_gateway = true
single_nat_gateway = false
one_nat_gateway_per_az = true
```

**Обоснование:**
- **Высокая доступность**: По одному NAT Gateway в каждой AZ предотвращает single point of failure
- **Производительность**: Распределение трафика между NAT Gateway
- **Изоляция отказов**: Проблема в одной AZ не влияет на другие
- **Соответствие требованиям**: Приватные инстансы могут получать обновления безопасности без публичного доступа

### 2.3 Kubernetes (EKS)
```
Cluster Version: 1.27
Node Groups: main (m5.large), medical (m5.2xlarge)
Disk Size: 50-100 GB
```

**Обоснование выбора версии и параметров:**

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| **Версия K8s** | 1.27 | LTS версия с долгосрочной поддержкой, стабильность критична для медицинских и финансовых сервисов |
| **Тип инстансов main** | m5.large (2 vCPU, 8 GB RAM) | Баланс стоимости и производительности для стандартных рабочих нагрузок |
| **Тип инстансов medical** | m5.2xlarge (8 vCPU, 32 GB RAM) | Ресурсоемкие ИИ-алгоритмы анализа медицинских изображений требуют значительных CPU и памяти |
| **Размер диска** | 50-100 GB | Запас для логов, кэша и временных данных. Для medical node group увеличен для хранения временных результатов анализа |
| **Taints для medical** | `domain=medical:NoSchedule` | Гарантирует, что медицинские workload не будут работать на общих нодах, обеспечивая изоляцию и предсказуемую производительность |

### 2.4 Базы данных
```
PostgreSQL: db.t3.large (2 vCPU, 8 GB RAM, 100 GB storage)
Redis: cache.t3.micro
```

**Обоснование:**
- **Managed Service**: AWS RDS и ElastiCache обеспечивают автоматические бэкапы, патчинг и мониторинг
- **Шифрование**: `storage_encrypted = true` обязательно для финансовых и медицинских данных
- **Auto-scaling storage**: `max_allocated_storage = 500` позволяет автоматически расти без downtime
- **Backup Retention**: 7 дней соответствует требованиям регуляторов для финансовых операций

### 2.5 Data Lake (S3)
```
Medical Data Lake: future-2-0-dev-medical-data
Financial Data Lake: future-2-0-dev-financial-data
```

**Обоснование:**
- **Разделение по доменам**: Изолированные бакеты предотвращают случайный доступ между медицинскими и финансовыми данными
- **Шифрование**: SSE-S3 включено по умолчанию
- **Версионирование**: Для аудита и восстановления данных
- **Lifecycle Policies**: Могут быть добавлены для автоматического перемещения старых данных в Glacier

### 2.6 Виртуальные машины для legacy
```
Instance Type: t3.medium (2 vCPU, 4 GB RAM)
Count: 2
Disk: 50 GB GP3 encrypted
```

**Обоснование:**
- **Минимальные требования**: Legacy системы (PowerBuilder) обычно не требуют высоких ресурсов
- **Бюджетный класс**: t3.medium предлагает баланс цены и производительности
- **Изоляция**: Работают в приватных подсетях, доступ только через VPN или jump host
- **План миграции**: Временное решение до полного перевода на контейнеры

## 3. Безопасность и соответствие требованиям

### 3.1 Security Groups архитектура
```
Иерархическая модель:
1. LB Security Group - только порты 80/443 из интернета
2. EKS Security Group - только из LB SG и между нодами
3. RDS Security Group - только из EKS SG
```

**Принцип наименьших привилегий**: Каждый ресурс имеет минимально необходимый доступ

### 3.2 Шифрование данных
- **At-rest**: Все диски (EBS, RDS) и S3 бакеты шифруются
- **In-transit**: TLS для всех сервисов, Security Groups разрешают только защищенные порты
- **KMS Integration**: Готовность для использования AWS KMS для customer-managed keys

### 3.3 IAM и RBAC
- **EKS IAM Roles for Service Accounts**: Изолированные права для каждого namespace
- **Отдельные роли для доменов**: medical-sa-role, fintech-sa-role
- **No broad policies**: Каждая роль имеет только необходимые permissions

## 4. Масштабируемость и устойчивость

### 4.1 Auto-scaling стратегия
```
EKS Node Groups:
- main: min=2, max=10, desired=3
- medical: min=2, max=6, desired=2
```

**Обоснование:**
- **Горизонтальное масштабирование**: Добавление нод вместо увеличения размера существующих
- **Разные политики**: Медицинские workload имеют более стабильные требования к ресурсам
- **Cluster Autoscaler**: Интеграция с Kubernetes для автоматического масштабирования

### 4.2 Multi-AZ развертывание
```
Распределение по 3 AZ:
- RDS: Multi-AZ deployment
- EKS Nodes: Распределены по AZ
- NAT Gateway: По одному в каждой AZ
```

**Бизнес-преимущество**: Доступность 99.95%+ соответствует SLA для финансовых и медицинских сервисов

## 5. Управление затратами (FinOps)

### 5.1 Выбор типов инстансов
- **T3 для dev/staging**: Burstable CPU для непостоянных нагрузок
- **M5 для production**: Стабильная производительность для production workload
- **Spot Instances для рабочих нод**: В dev средах можно использовать spot для снижения затрат на 70-90%

### 5.2 Стратегия остановки ресурсов
```
Dev Environment:
- Автоматическое остановление RDS в нерабочее время
- Scaling to zero для dev нод
- S3 Lifecycle для архивации старых данных
```

**Экономический эффект**: Снижение затрат на dev среды на 40-60%

## 6. Интеграция с существующими системами

### 6.1 Поддержка legacy систем
- **Выделенные VM**: Для постепенной миграции от PowerBuilder
- **VPN доступ**: Безопасный доступ к legacy системам
- **Постепенная миграция**: Инфраструктура позволяет мигрировать по одному сервису за раз

### 6.2 Готовность к интеграции
- **API Gateway patterns**: Структура VPC готова для размещения API Gateway
- **Event Bridge готовность**: Security Groups позволяют интеграцию с AWS EventBridge
- **Гибридная архитектура**: Возможность подключения к on-premise системам через Direct Connect/VPN

## 7. Мониторинг и observability

### 7.1 Встроенные возможности
- **CloudWatch Integration**: Все ресурсы отправляют метрики
- **VPC Flow Logs**: Для аудита сетевого трафика
- **S3 Access Logs**: Для отслеживания доступа к данным

### 7.2 Готовность к расширению
- **Prometheus-ready**: EKS настроен для сбора метрик
- **EFK Stack совместимость**: Security Groups разрешают необходимые порты
- **Custom Metrics**: Архитектура поддерживает custom metrics через CloudWatch Agent
